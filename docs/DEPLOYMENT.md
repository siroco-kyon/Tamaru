# 社内LANでの設置

Tamaruは社内LAN向け・認証必須のWebアプリです。設置先サーバーへのインストール、証明書の作成、ファイアウォールの変更、常駐タスクの登録を、このリポジトリの取得だけで自動実行することはありません。

v0.1.1には将来用の削除処理が含まれますが、実行経路は接続されていません。追加の削除権限や退避先の設定は今は不要です。収集アカウントの共有への権限は、引き続き一覧・属性の読み取りだけで運用できます。設定・環境変数・起動引数から削除を有効にすることはできません。

## 1. 保存先と実行アカウント

- アプリ: 例 `C:\Apps\Tamaru`。Watashiとは別フォルダにします。
- データ: 例 `C:\TamaruData`。ローカルの書き込み可能な場所に置き、Web配信するフォルダの外にします。
- データへのアクセスは実行アカウントと必要なサーバー管理者に限定します。
- 実行アカウントには、収集対象の共有フォルダへの一覧取得・属性取得権限と、データ保存先への書き込み権限が必要です。
- 収集対象は `\\server\share\受け渡し` のようなUNCパスで設定します。対話ログイン時だけの割り当てドライブは使いません。

サイトにログインするTamaru管理者と、共有へ接続するWindowsの実行アカウントは別です。管理者を追加しても、その人のWindows権限で共有を走査するわけではありません。

## 2. 初期管理者

サーバー上で、管理データを置く場所を指定して対話登録します。

```powershell
.\Tamaru.exe --state C:\TamaruData create-admin admin --display-name 管理者
```

パスワードは12〜256文字です。コマンド引数やGitHubに書かず、対話入力してください。2人目以降はログイン後の「管理者管理」で追加します。全管理者が他の管理者の変更もできるため、管理を任せる人だけ登録します。

## 3. HTTPSで待ち受ける（直接公開）

社内で信頼されるサーバー証明書と秘密鍵をPEM形式で用意します。鍵へのアクセスは実行アカウントに限定します。証明書のホスト名に合わせて社内DNSを設定します。

```powershell
.\Tamaru.exe --state C:\TamaruData serve `
  --host 0.0.0.0 --port 8765 `
  --allowed-host tamaru.example.local `
  --cert-file C:\TamaruCertificates\server.crt `
  --key-file C:\TamaruCertificates\server.key
```

管理者は `https://tamaru.example.local:8765/` を開きます。IPでアクセスする場合は、そのIPに対する証明書と`--allowed-host`も必要です。必要なホストは引数を繰り返して指定できます。`*`での無制限許可は使わないでください。

Windowsファイアウォールは、必要なポートをDomain/Privateプロファイルと管理PCのIPまたは社内サブネットに限定して許可します。Publicプロファイルやルーターのポート転送で外部公開しません。

Tamaru自身もIPv4の10/8・172.16/12・192.168/16・169.254/16・127/8、IPv6のULA・リンクローカル・ループバックを許可し、その他を拒否します。グローバルアドレスを社内で使う環境は、この版の標準構成では対象外です。

## 4. IISなどでHTTPSを終端する場合

既存のIISを使う場合も、Tamaruは別サイト・別プロセスとして動かします。Watashiの設定やコードを変更する必要はありません。IIS側にTLS終端とリバースプロキシ機能を用意します。

Tamaruはループバックだけで待ち受け、信頼するプロキシのIPを明示します。

```powershell
.\Tamaru.exe --state C:\TamaruData serve `
  --host 127.0.0.1 --port 8765 `
  --allowed-host tamaru.example.local `
  --trusted-proxy 127.0.0.1
```

プロキシ側でHostを保持し、転送先へ渡す`X-Forwarded-For`と`X-Forwarded-Proto`を信頼できる元の値に設定します。クライアントが送った偽の転送ヘッダーは、そのまま引き継がない設定にしてください。Tamaruは、明示したプロキシからのヘッダーだけを信頼します。外向きにHTTPのまま公開するための機能ではありません。

バックエンドの8765番ポートをLANへ開ける必要はありません。IIS側のHTTPSポートだけを社内向けに許可します。プロキシ経由でも接続元がLAN内であることとHTTPSを確認します。

## 5. 再起動後も動かす

アプリ内の日次スケジュールは、サーバープロセスが起動している間だけ動きます。Windowsでは、タスクスケジューラーでサーバー起動時にTamaruを常駐起動する構成が使えます。

| 項目 | 設定例 |
|---|---|
| トリガー | システム起動時。必要ならネットワーク準備のため1分遅延 |
| プログラム | `C:\Apps\Tamaru\Tamaru.exe` |
| 引数 | 上記の`--state ... serve ...`全体 |
| 開始フォルダー | `C:\Apps\Tamaru` |
| 実行ユーザー | 共有を読め、管理データへ書き込めるWindowsアカウント |
| ログオン条件 | ユーザーのログオンにかかわらず実行 |
| 実行時間の制限 | 常駐なので、既定の「3日で停止」などの制限を外す |
| 失敗した場合 | 1分後に再起動などを設定 |
| 重複起動 | 新しいインスタンスを開始しない |

共有への認証が必要なため、資格情報を保存しないS4Uの設定ではネットワーク共有へアクセスできない場合があります。設置先のドメイン運用に合ったアカウント・タスク設定を選び、**ログオフ状態とサーバー再起動後の両方で実際の共有を収集できること**を確認してください。

この起動タスク自体を「毎日1回だけ起動」にすると、Web閲覧や手動収集の時間に動いていない状態になります。Tamaruは常駐させ、1日1回の収集時刻はWeb画面で設定します。

Uvicornは1 workerで動かします。複数workerや複数インスタンスを同じデータ保存先で動かす構成には対応しません。サーバー側のlockファイルでも重複起動を拒否します。

## 6. 最初の動作確認

1. 管理PCからHTTPSでログインでき、未ログインでは一覧・CSVを取得できないこと。
2. 対象のUNCパスを設定し、手動収集を実行できること。
3. 既存ファイルが0日で出て、実際の件数・容量・所在と合うこと。
4. 翌日または再収集で初回検出日時が維持されること。
5. 追加した管理者でログインでき、無効化・パスワード変更で既存ログインが解除されること。
6. 日次時刻の収集履歴に`scheduler`が出ること。
7. サーバー再起動・ログオフ後も動作すること。
8. 管理データのバックアップと復元ができること。

実ファイルや本番の管理者アカウント情報を、GitHubや動作確認用のスクリーンショットへ含めないでください。
